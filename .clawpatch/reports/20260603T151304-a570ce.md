## high: Async navigation leaves stale file rows actionable under the new location

id: fnd_sig-feat-ui-flow-ccbda03ee7-2c0c_e3a3cc164c
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Apple source Grove/Controllers#1 (feat_ui-flow_ccbda03ee7)

evidence:
- Grove/Controllers/FileListViewController.swift:418-434 (FileListViewController.loadDirectory)
- Grove/Controllers/FileListViewController.swift:489-502 (FileListViewController.reloadContents)
- Grove/Controllers/FileListViewController.swift:646-650 (FileListViewController.selectedItems)
- Grove/Controllers/IconViewController.swift:113-122 (IconViewController.loadDirectory)
- Grove/Controllers/GalleryViewController.swift:148-157 (GalleryViewController.loadDirectory)

The list, icon, and gallery controllers update currentURL and start an async directory load without first clearing the old items or disabling commands. In FileListViewController, assigning filterText immediately reapplies the previous allItems before the async callback replaces them. During that window the UI can show and operate on files from the old folder while the controller state already says it is in the new folder, so destructive commands can target stale selectedItems.

recommendation:
On loadDirectory, clear items/allItems and selection immediately, reload the view, show a loading/empty state, and disable file actions until the matching generation completes. Do the same for icon and gallery views before starting contentsOfDirectoryAsync.

test analysis:
No linked controller tests cover navigation while directory loading is pending or verify that stale rows are cleared before async results arrive.

suggested regression test:
Add a controller-level test with a delayed directory loader: navigate from a populated folder to another URL and assert rows and selectedItems are empty or actions disabled before the delayed result is delivered.

minimum fix scope:
Update FileListViewController, IconViewController, and GalleryViewController directory-loading state transitions.

repro:
Select a file in folder A, navigate to a slow or unreadable folder B, then quickly invoke an action such as Move to Trash before the async load callback runs. The selection still comes from A while the browser has already navigated to B.

## high: Move-replace rollback can delete the moved source when backup cleanup fails

id: fnd_sig-feat-ui-flow-41a384a183-787a_ce8ac0e875
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Apple source Grove/Services (feat_ui-flow_41a384a183)

evidence:
- Grove/Services/FileOperationService.swift:356-368 (FileOperationService.performReplacingTransfer)
- Grove/Services/FileOperationService.swift:320-327 (FileOperationService.transfer)
- GroveTests/FileOperationServiceTests.swift:75-86 (FileOperationServiceTests.testReplaceRestoresDestinationWhenIncomingTransferFails)

The do/catch covers both the incoming transfer and the later backup deletion. For a replace move, a successful performTransfer moves the only source copy into destinationURL. If removing backupURL then throws, the catch removes destinationURL before restoring the old backup, which deletes the moved source and reports only a failure.

recommendation:
Separate transfer failure rollback from backup cleanup failure. After the incoming move succeeds, never delete destinationURL just because backup cleanup failed; either leave the successful replacement plus leftover backup and report cleanup, or move destinationURL back to sourceURL before restoring the old destination.

test analysis:
The existing replace test covers only failure before the incoming transfer succeeds, using copy with a missing source. It does not cover failure from removeItem(at: backupURL) after a successful move.

suggested regression test:
Add a moveResolvingConflictsWithRecords .replace test where backup removal fails after source move, using a controlled file-manager abstraction or an undeletable backup directory, and assert the source content still exists either at the destination or restored source path.

minimum fix scope:
FileOperationService.performReplacingTransfer rollback phase handling for .move replacements.

repro:
Move a file/folder over an existing destination using .replace, with the destination backup made undeletable after it is moved aside; the source is moved into place, backup removal throws, and the catch deletes the moved source while restoring the old destination.

## high: Open in Terminal allows shell command substitution from filenames

id: fnd_sig-feat-ui-flow-ccbda03ee7-6bd3_12816092a7
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Apple source Grove/Controllers#1 (feat_ui-flow_ccbda03ee7)

evidence:
- Grove/Controllers/FileListViewController.swift:1614-1629 (FileListViewController.contextOpenInTerminal)

The selected path is interpolated into a Terminal command as cd "..." after only backslashes and double quotes are escaped. Shell double quotes still evaluate command substitutions such as $() and backticks, so opening Terminal in a directory whose name contains command substitution can execute arbitrary shell commands under the user's account.

recommendation:
Build the Terminal command using a real shell-quoted path, for example AppleScript's quoted form of the POSIX path, and keep AppleScript string escaping separate from shell escaping.

test analysis:
No linked tests were provided for this controller feature, and this requires a malicious filesystem-name case through the context-menu Terminal action.

suggested regression test:
Add a unit test around the script/command builder with paths containing $(), backticks, quotes, spaces, and apostrophes, asserting the generated command cannot perform shell substitution.

minimum fix scope:
Change FileListViewController.contextOpenInTerminal path quoting or extract a safe command builder used by that action.

repro:
Create or select a folder named $(touch /tmp/grove-terminal-pwn), choose Open in Terminal, and the generated Terminal command will evaluate the substitution before cd runs.

## medium: Drop handlers turn any source that allows move into an actual move

id: fnd_sig-feat-ui-flow-ccbda03ee7-bfe1_6fc6235278
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Apple source Grove/Controllers#1 (feat_ui-flow_ccbda03ee7)

evidence:
- Grove/Controllers/FileListViewController.swift:1005-1020 (FileListViewController table drop handling)
- Grove/Controllers/IconViewController.swift:270-312 (IconViewController collection drop handling)
- Grove/Controllers/BrowserWindowController.swift:484-502 (BrowserWindowController file drop handling)

The code treats draggingSourceOperationMask.contains(.move) as the user's chosen operation in both validation and accept. That mask describes operations the source permits, not necessarily the negotiated copy-vs-move intent. A drag source that advertises both copy and move will be moved even when the user expects a copy.

recommendation:
Choose and persist the actual negotiated operation for the drag session. Default to copy unless move is explicitly selected, and pass that selected operation into the transfer call instead of recomputing from the source capability mask in acceptDrop.

test analysis:
No linked tests simulate AppKit drag masks or modifier-driven copy/move negotiation across these drop targets.

suggested regression test:
Add drag/drop tests or fakes where the source mask is [.copy, .move] but the requested operation is copy, and assert the controllers call copy transfer paths.

minimum fix scope:
Fix drop validation and accept logic in BrowserWindowController, FileListViewController, and IconViewController.

repro:
Drag files from a source that permits both copy and move and request a copy operation, such as with the standard copy modifier. These handlers still return and execute move because .move is present in the allowed mask.

## medium: Large downloads and checksums buffer entire files in memory

id: fnd_sig-feat-ui-flow-41a384a183-2cf3_5b2522e938
category: performance
confidence: high
triage: risk
status: open
feature: Apple source Grove/Services (feat_ui-flow_41a384a183)

evidence:
- Grove/Services/AWSS3Gateway.swift:122-143 (AWSS3Gateway.downloadObject)
- Grove/Services/FileOperationService.swift:620-636 (FileOperationService.computeChecksum)
- GroveTests/S3BrowserServiceTests.swift:201-234 (S3BrowserServiceTests.testDownloadUsesUniqueDestinationForDirectoryConflicts)

S3 downloads call readData() before writing, so the whole object must fit in RAM and progress cannot advance until the object has already been read. Local checksum calculation has the same whole-file allocation pattern. In a file browser, multi-GB objects or local files can cause memory pressure or termination.

recommendation:
Stream S3 response chunks directly to a FileHandle at temporaryURL while updating progress, and compute checksums incrementally from a FileHandle/InputStream rather than Data(contentsOf:).

test analysis:
The S3 download tests use tiny in-memory Data payloads and assert destination conflict/cleanup behavior. There are no checksum tests and no test that would expose memory growth or chunked progress behavior.

suggested regression test:
Add chunked download/checksum tests around a streaming abstraction: verify a file larger than the chunk size is processed incrementally, progress advances before completion, and the resulting bytes/hash match expected values.

minimum fix scope:
AWSS3Gateway.downloadObject and FileOperationService.computeChecksum streaming implementations.

repro:
Download a multi-GB S3 object or compute a checksum for a multi-GB local file; the service allocates a Data buffer roughly the size of the file before completing the operation.

## medium: S3 object locations rewrite object keys as folder prefixes

id: fnd_sig-feat-ui-flow-2c88f036ff-bfd8_a019d3261c
category: bug
confidence: high
triage: confirmed-bug
status: open
feature: Apple source Grove/Models (feat_ui-flow_2c88f036ff)

evidence:
- Grove/Models/StorageLocation.swift:47-52 (S3Location.init(profileName:regionOverride:bucket:prefix:))
- Grove/Models/StorageLocation.swift:102-104 (S3Location.objectLocation(key:))
- Grove/Models/StorageLocation.swift:146-160 (S3Location.normalizedPrefix(_:isFolder:))
- Grove/Models/BrowserItem.swift:119-124 (BrowserItem.storageLocation)

S3 object keys are modeled through objectLocation(key:), but that method first applies path-like normalization and then passes the result into the public S3Location initializer. The initializer unconditionally normalizes as a folder, so an object key such as logs/app.txt becomes logs/app.txt/. The same normalization also strips leading slashes, collapses repeated slashes, trims whitespace, and maps dot-only keys to empty. BrowserItem exposes the resulting S3Item.location as the item's StorageLocation, so callers that navigate, persist, breadcrumb, or otherwise act on storageLocation can address a different S3 key or treat an object as a prefix.

recommendation:
Separate folder-prefix normalization from object-key preservation. Add an initializer or factory that can store an already-normalized object key without appending a slash, and have objectLocation(key:) preserve exact object keys while prefix navigation continues to normalize folder prefixes.

test analysis:
The included NavigationHistoryTests exercise only local URL history and do not assert S3Location.objectLocation or BrowserItem.storageLocation behavior for S3 objects.

suggested regression test:
Add a storage model test asserting that S3Location(profileName: "ops", regionOverride: "us-east-1", bucket: "bucket", prefix: "").objectLocation(key: "logs/app.txt").prefix == "logs/app.txt", and that BrowserItem.s3(object).storageLocation preserves the same object key without a trailing slash.

minimum fix scope:
Grove/Models/StorageLocation.swift, with any S3 object construction call sites adjusted only as needed to preserve the object-vs-prefix distinction.

id: fnd_sig-feat-ui-flow-41a384a183-9e52_14b7bbec71

confidence: medium
triage: contract-mismatch
status: open

- Grove/Services/AWSS3Gateway.swift:158-171 (AWSS3Gateway.client)
- Grove/Services/AWSS3Gateway.swift:184-192 (AWSS3Gateway.makeClient)
- Grove/Services/AWSS3Gateway.swift:306-311 (NoRefreshSSOCredentialProvider.resolve)

The gateway resolves SSO role credentials once, wraps them in a static resolver, and caches the S3Client by profile and region forever. test analysis:
AWSProfileStoreTests exercise NoRefreshSSOCredentialProvider directly and S3BrowserServiceTests use MockS3Gateway. No test instantiates AWSS3Gateway or verifies cached-client behavior across SSO role credential expiration and external refresh.

suggested regression test:
Add an AWSS3Gateway-level test with injectable client/provider factories that returns short-lived SSO credentials, advances time past expiration, refreshes the provider output, and asserts a new client or fresh identity is used for the next request.

minimum fix scope:
AWSS3Gateway client cache policy and SSO credential resolver wiring.

repro:
Use an SSO profile until its role credentials expire, refresh the profile outside Grove, then retry the same profile/region in the same app session; AWSS3Gateway.client returns the previously cached S3Client instead of constructing one from fresh role credentials.
